# AGENTS.md

Проект: Telegram-бот StreetBuddy на TypeScript + Cloudflare Workers.
БД: Cloudflare D1 (SQLite). Распознавание номера: Workers AI.
Логика, не зависящая от мессенджера, — в `src/core`; Telegram (диалог, кнопки, шаг жалобы) — в `src/telegram`.
Спецификация — `docs/architecture.md`. Этот файл его не заменяет и не дублирует,
а добавляет проверяемые технические ограничения для работы с кодом.
Отложенные задачи — в `docs/pending.md`. Почему код устроен именно так — в `docs/decisions.md`.

Локальная папка проекта на машине владельца: `~/YouMustHaveBeen/StreetBuddy`. Терминальные команды для нее —
с `cd ~/YouMustHaveBeen/StreetBuddy`, не с путем агентского контейнера (`/home/claude/streetbuddy` и т.п. —
это не ее машина).

## Главное правило

Не оптимизируй и не рефактори код сверх поставленной задачи.
Ничего не добавляй от себя: каждая функция, кнопка, проверка и запрос должны соответствовать
подтвержденному решению и `docs/architecture.md`. Если для задачи нужно что-то, чего в спецификации нет
или что ей противоречит, — сначала покажи, где именно противоречие, и дождись подтверждения.
Замечание автоматического ревьюера не является подтверждением: любое изменение поведения сверх узкого
багфикса называется отдельно и подтверждается отдельно, а не входит в общий пакет под одно «пиши».

Перед записью или изменением любого кода/файла задается вопрос «можно писать код?» отдельным сообщением,
ответ ждется. Ответ на вопрос по содержанию — не разрешение. Вопрос не задается, пока в обсуждении есть
открытые вопросы, требующие ответа владельца, — только когда на все получен ответ.

Если фикс требует нового или измененного пользовательского текста (кнопки, сообщения бота, шаблон
описания, страница инструкции), а владелец не давал точную формулировку — не писать текст самостоятельно.
Остановиться, показать текущий текст и в чем проблема, и ждать точную формулировку отдельным шагом.

Интерфейс бота — на английском. В коде никогда не используется буква «ё» — только «е».

## Ветки, PR, merge

1. Работа всегда идет через ветку, прямых коммитов в `main` нет. Единственное исключение — правка только
   документации (спецификация, страница инструкции).
2. Создание ветки и создание PR — каждое только после отдельного явного «да» владельца.
   Запрос ревью на уже открытом PR отдельного «да» не требует, но ревью у Copilot не запрашивать никогда.
3. Merge в `main` — только после отдельного явного «да» на каждое слияние.
4. Перед любым PR сверить изменение со ВСЕЙ спецификацией, а не только с относящимся разделом.
5. Документацию проекта (`docs/architecture.md`, страница инструкции и т.д.) обновлять в том же PR,
   а не после слияния.
6. Личные данные: настоящие имя и email владельца не должны встречаться нигде — ни в коммитах, ни в логах,
   ни в коде, ни в комментариях (репозиторий может стать публичным).
7. Коммиты и push делает агент сам, а не владелец. Если доступа к репозиторию с правом push нет, сразу подключить
   его (`add_repo` с `access: push`) и спросить разрешение скачать репозиторий в облачное окружение; не отправлять
   владельца в терминал за `git push`.

## Личные данные пользователей

1. Имя, телефон, email и адрес пользователя никогда не попадают на сервер бота: их хранит и подставляет
   только скрипт на телефоне. Бот готовит только ссылку с данными о нарушении.
2. Фото обрабатывается в памяти и не сохраняется. В логи не писать фото, номера машин, координаты,
   Telegram ID и тексты жалоб.
3. Сроки хранения в D1 — ровно по `docs/architecture.md` (раздел «Приватность и безопасность»); не добавлять
   поля и таблицы с личными данными, которых там нет.

## Модуль core и Telegram

1. `src/core` ничего не знает о Telegram: никаких импортов из `src/telegram`, типов и терминов Telegram.
   Его потом использует WhatsApp.
2. Все вызовы Telegram — только через `src/telegram`. Прямой `fetch` к `api.telegram.org` вне этого модуля
   запрещен.
3. Вебхук Worker проверяет секретный токен, сразу отвечает Telegram, а долгую работу (распознавание)
   выполняет в фоне через `waitUntil`. Повторные обновления отсекаются по `update_id`.
4. Acknowledgment кнопки / снятие «часиков» отправляется как можно раньше, а не после всех чтений из D1,
   если это не меняет бизнес-логику.
5. Бот доступен только участникам закрытой группы; проверку членства не дублировать в разных местах —
   одна общая проверка на входе.

## Внешние сервисы

1. Nominatim (OpenStreetMap): свой User-Agent, не чаще 1 запроса в секунду, результаты кешируются.
2. Workers AI: подключается привязкой `AI`, без ключа. Модели — только из списка в спецификации.
   Llama 3.2 Vision и Llama 4 Scout не использовать: их лицензия не дает прав разработчику из ЕС.
3. Одно и то же фото не распознается повторно: результат хранится по постоянному ID файла в Telegram.
4. Место проверяется до распознавания номера, чтобы фото из чужого района не тратили лимит.
5. Район и графство берутся из `config/area.geojson`, а не из кода.

## Скрипт заполнения формы

1. Никогда не ставит подтверждающие галочки, не нажимает «Submit Report» и не трогает капчу.
2. Данные из ссылки вставляются в поля только как текст, без `innerHTML`, после проверки структуры,
   допустимых значений, длины и формата даты.
3. Если поле формы не найдено — сообщить, что форма изменилась и нужно заполнить вручную; у скрипта есть
   номер версии. Изменение скрипта и ежедневной проверки формы согласуются между собой.

## D1 / SQL

1. Для новых и измененных запросов к растущим таблицам:
   - объясни выбор индексов с учетом условий и сортировки;
   - проверь `EXPLAIN QUERY PLAN` на тестовой базе;
   - полный просмотр таблицы требует объяснения, но не запрещен автоматически;
   - не добавляй индекс только ради формального соблюдения правила.
2. Запрещен N+1: SQL-запросы внутри цикла по строкам. Используй `IN (...)`, `JOIN`, batch-запрос
   или предварительную выборку.
3. Один пользовательский сценарий (нажатие кнопки, сообщение) — обычно не более 2–3 запросов к D1.
   Если нужно больше — явный комментарий `// QUERY BUDGET EXCEPTION` с короткой подписью (какие запросы) и объяснение в PR.
4. Не читай одну и ту же строку/настройку несколько раз в рамках одного запроса и не читай из БД запись,
   которая была только что записана и уже доступна в памяти.
5. Любая таблица, которая может бесконечно расти, должна иметь правило очистки со сроком из
   `docs/architecture.md`; если его еще нет, это отдельная задача, а не блокер текущей.
6. Любое изменение схемы или индексов — только новой миграцией. Уже примененные файлы миграций не менять.
   Миграции создаются через `npx wrangler d1 migrations create <DB_NAME> <short_description>`.
7. Любой `LIKE '%...%'` с пользовательским текстом экранирует `%`, `_`, `\` и укладывается в лимит D1
   на шаблон LIKE/GLOB — 50 байт вместе с `%` и экранированием (русские и ирландские буквы занимают
   больше одного байта, поэтому обрезать по числу символов нельзя).

## Повторное использование

1. Перед созданием функции найди существующую реализацию.
2. Общие операции — только через существующие сервисы/хелперы. Новая копия существующей логики запрещена
   без объяснения в PR.
3. Не добавляй неиспользуемые экспорты, типы, функции, поля и импорты.

## Комментарии в коде

Комментарий объясняет только, что код делает. Все «почему» (почему решено так, а не иначе, обходы особенностей
Telegram/D1/Workers AI/формы Traffic Watch, почему проверка или порядок операций именно такие) записываются
в `docs/decisions.md`, а не в код. Единственное исключение — метка `QUERY BUDGET EXCEPTION` с короткой подписью.
Не писать в комментариях даты, «решение DD.MM», номера PR, номера пунктов ревью/обсуждения/плана,
упоминания ревьюеров (CodeRabbit, Sourcery и т.п.) и «раньше было/было заменено на».
Имя владельца не должно встречаться в комментариях и строках кода вообще.

## Перед завершением задачи

1. Перечислить новые/измененные SQL-запросы с указанием индексов.
2. Указать число запросов к D1 и вызовов Telegram в основном сценарии задачи.
3. Проверить, нет ли N+1, лишних чтений и дублей.
4. Запустить `npm run typecheck` (и `npm test`, если тесты уже есть в проекте).
5. Если какое-то правило нарушено — остановиться и спросить, а не делать обходное решение.
6. Задача (включая ревью/проверку по списку пунктов) выполняется полностью, без самовольного урезания
   объема ради экономии времени/усилий — если нужно сократить, сначала спросить.

## Перед merge

1. Прочитать все комментарии и ревью на PR (включая ботов) и ответить на них — фикс в коде или объяснение,
   почему не фиксится — прежде, чем предлагать merge.
2. Если в репозитории есть автоматическая проверка (GitHub Actions), она должна быть зеленой на последнем
   коммите PR. Красная — не сливать, сначала починить.
3. Проверить, не занят ли номер новой миграции другим открытым PR; если занят — переименовать свою.

## После merge (команды для владельца)

Выполняются на ее машине, не в контейнере агента.

1. Каждый блок команд начинается с `cd ~/YouMustHaveBeen/StreetBuddy`. Перед деплоем и применением
   миграций — `git checkout main` и `git pull` в том же блоке: локальная копия сама не обновляется,
   и устаревший деплой или «No migrations to apply!» обычно именно из-за этого.
2. Wrangler вызывается через `npx wrangler ...` (в PATH его нет). Миграции — `npx wrangler d1 migrations
   apply <DB_NAME> --remote`, деплой — `npx wrangler deploy`.
3. Если wrangler падает с `7403 "account is not valid or is not authorized"` при правильном аккаунте
   в `whoami` — это протухший локальный OAuth-токен: `npx wrangler logout`, затем отдельной командой
   `npx wrangler login` (откроет браузер), затем повторить команду.
4. Секреты (`TELEGRAM_BOT_TOKEN`, `WEBHOOK_SECRET`) задаются через `npx wrangler secret put`, а не
   хранятся в файлах репозитория.
5. Команда с интерактивным вопросом y/n дается отдельно, остальные команды одной задачи — одним блоком,
   строка за строкой, без `&&`.
